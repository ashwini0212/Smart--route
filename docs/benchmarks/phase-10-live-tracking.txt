Reading:
- A sweep over 48 drivers with active deliveries takes 1.6-2.6 s, which is ~35-55 ms per driver: it computes
  a cost matrix and a visiting order per driver (Phase 8 measured the matrix as the expensive part). At the
  default 15 s interval that is about 15 % of one core, continuously. It does not scale to a few hundred
  active drivers on one instance, and the fix is not a faster sweep but a smaller one: re-check only the
  drivers whose orders or road network actually changed.
- The live map's delay is dominated by the outbox relay's polling interval (Phase 9 measured the same thing),
  not by Kafka, Redis or SSE: 500 ms interval gives p50 ~0.5 s, 50 ms gives p50 0.12 s.
- The 50 ms run on a single scheduler thread was the slowest of the four (p50 613 ms, p95 5.5 s, worst case
  29 s), which is the opposite of what a faster relay should do. Cause: Spring's scheduler runs one thread by
  default, and everything scheduled shares it - the relay, the 2 s tracking sweep, the driver simulator and
  the heartbeat. A faster relay simply competed for the same thread more often. With 4 threads the same
  configuration gives p50 122 ms / p95 219 ms, and the default interval improves from p95 1.9 s to 0.9 s.
  The pool size is now a setting (SCHEDULING_THREADS, default 4).
- Frames arrive at 16-19/s with ~48 drivers moving every 2 s, which is the simulator's rate, not a limit.
  One sequential client on the same machine; this says nothing about many dashboards at once.
